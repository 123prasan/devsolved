Payment Service Outage — Checkout Failures Across EU Region (100% Error Rate)

postgres connection-pool eu-west-1 checkout pgbouncer
Priya Raghavan Jul 18, 2026 — 14:32 UTC MTTR: 2h 39m 3,847 views 142 upvotes
Executive Summary

On July 18, 2026, the EU-West-1 payment service experienced a complete checkout outage lasting 2 hours 39 minutes. The root cause was a misconfigured PgBouncer connection pool limit (max_client_conn: 50) that was not updated after a 3× traffic scaling event the previous week. Connection exhaustion caused all new database queries to time out. Approximately 14,200 checkout attempts failed, resulting in an estimated €420K in deferred revenue. The incident was resolved by hot-patching PgBouncer configuration and restarting the pool manager without a full service restart.

At 14:08 UTC on July 18, the EU payments service began returning HTTP 503 errors on all /api/v2/checkout/confirm endpoints. Symptom

All checkout confirmation requests in EU-West-1 began failing with 503 responses. No errors were observed in US or APAC regions.

  • HTTP 503 error rate: 100% on /api/v2/checkout/confirm (EU-West-1)
  • PagerDuty alert: "payments-eu: checkout_error_rate > 5% for 3m" fired at 14:11 UTC
  • Grafana: p99 latency on payments-db-eu spiked from 12ms to 30,000ms (timeout)
  • Sentry: "connection pool exhausted" errors flooding in at ~200/s
  • Customer support: 47 tickets opened within first 30 minutes reporting failed payments
  • No anomalies in US-East-1 or APAC-Southeast-1 clusters

Root Cause

The PgBouncer connection pool max_client_conn limit of 50 was not updated when EU checkout traffic tripled following the Black Friday preview campaign launch on July 11.

At 540 RPS with an average query duration of ~12ms, the checkout service requires approximately 6–7 concurrent database connections per app replica × 8 replicas = ~56 concurrent connections at baseline. The existing max_client_conn=50 was adequate at 180 RPS but became a hard ceiling at 3× load. Once all 50 slots were occupied, new requests queued and eventually timed out at the application layer (30s timeout), producing 503 responses. The RDS instance itself had capacity for 200+ connections but PgBouncer never forwarded the traffic to it.

Resolution Steps

The fix was applied as a hot-patch to PgBouncer configuration without requiring a full service restart. PgBouncer supports live config reload via RELOAD command, which allowed the fix to be applied in under 90 seconds.

/etc/pgbouncer/pgbouncer.ini (after fix) ini 
1[pgbouncer]
2; Updated values — sized for 4x expected peak traffic
3max_client_conn = 500      ; was 50 — increased 10x
4default_pool_size = 40     ; was 10 — sized for RDS max_connections=200
5min_pool_size = 10         ; was 2
6reserve_pool_size = 20     ; was 5
7reserve_pool_timeout = 3
pgbouncer-eu — apply fix
kubectl cp pgbouncer.ini payments/pgbouncer-eu-0:/etc/pgbouncer/pgbouncer.ini
pgbouncer.ini copied successfully

Resolution

PgBouncer config was hot-reloaded at 16:44 UTC. Error rate dropped to 0 within 45 seconds. Full checkout functionality restored by 16:46 UTC. Monitoring confirmed stable operation for 25 minutes before incident was marked resolved at 17:11 UTC.

  • Updated max_client_conn from 50 to 500 (10× headroom for current traffic)
  • Updated default_pool_size from 10 to 40 (sized for RDS max_connections=200)
  • Hot-reloaded PgBouncer config via RELOAD command — no service restart required
  • Confirmed cl_waiting dropped to 0 within 30 seconds of reload
  • Verified checkout error rate reached 0 within 45 seconds
  • Monitored for 25 minutes before marking incident resolved

Lessons Learned

This incident highlights a classic operational gap: infrastructure limits were not treated as code. PgBouncer's max_client_conn was a manually-set value with no automated review trigger when traffic patterns changed. The fix was trivial once identified — the 2h 39m MTTR was entirely investigation time, not remediation time.

  • Traffic scaling runbooks must include a checklist of all connection pool and rate limit configurations that need review
  • Infrastructure limits like max_client_conn should be derived from traffic metrics, not set manually
  • PgBouncer pool saturation (cl_waiting > 0) should alert before exhaustion occurs — we had no early warning signal
  • The 90-second fix time vs. 2h 39m investigation time shows our observability gap: pool metrics were not surfaced in our primary dashboards
  • Staging validation of config changes should use production-representative traffic load
